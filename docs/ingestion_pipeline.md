# Импорт публикаций в D1

Реализован локальный клиент и закрытый API Worker для импорта сохранённых результатов двух коллекторов. Импорт не запускается по расписанию, не получает данные с сайтов самостоятельно и не отправляет Telegram-сообщения. Production Worker и секреты этой фазой не настраиваются.

## API и аутентификация

- `GET /internal/source-states?source=folketinget|hoeringsportalen` — возвращает независимые состояния потоков.
- `POST /internal/ingest` — действия `start`, `batch`, `commit`, `abort`.
- Для обоих маршрутов обязателен `Authorization: Bearer <INGEST_API_TOKEN>`. Проверка выполняется до чтения тела и БД. Ответы не содержат токенов или содержимого запросов.
- Тело ограничено 256 KiB; пакет — 50 публикаций; запуск — максимум 200 пакетов; обработка commit — максимум 20 записей за запрос.

Токен должен быть отдельным Worker Secret с именем `INGEST_API_TOKEN`, не Telegram-секретом. Для локального теста используется только локальная переменная окружения. Перед будущим production-использованием ответственный оператор должен отдельно создать случайный секрет и настроить его в Cloudflare Dashboard; этот репозиторий его не генерирует и не хранит.

## Контракт

Клиент читает JSON от имеющихся коллекторов, применяет `collectors.relevance.classify` и отправляет записи следующей формы (сокращённо):

```json
{
  "source": "folketinget",
  "external_id": "12345",
  "title": "Оригинальный заголовок",
  "url": "https://oda.ft.dk/api/Sag(12345)",
  "relevance": "POTENTIAL",
  "relevance_reason": "...",
  "ruleset_version": "1.1",
  "status": "Fremsat",
  "publication_type": "L 1",
  "published_at": null,
  "source_updated_at": null,
  "source_updated_at_raw": "2026-10-16T10:11:12.1234567",
  "historical": false,
  "notification_blocked": false,
  "complete": true,
  "diagnostics": [],
  "source_metadata": {"status_id": 2},
  "normalized_snapshot": {
    "title": "Оригинальный заголовок",
    "status": "Fremsat",
    "documents": [{"id": 7, "link_id": 8, "title": "Lovudkast"}],
    "stages": [],
    "votes": []
  }
}
```

Сервер проверяет source, числовой официальный ID, домен и формат URL, enum-категории, даты, типы и размеры связей. Для Høringsportalen разрешён URL карточки; для ODA — API-ссылка на Sag. Источники разрешаются по имеющимся строкам `sources`, повторные справочники не создаются. SQL из клиента не принимается.

## Клиент

Клиент использует только стандартную библиотеку Python и не делает запросов к источникам:

```sh
python3 -m collectors.ingestion_client saved-output.json --source folketinget --mode historical --dry-run
```

Для явной отправки нужно передать `INGEST_API_URL` и `INGEST_API_TOKEN` через окружение и убрать `--dry-run`. URL задаётся как базовый адрес Worker. `--run-id <UUID>` продолжает отправку того же запуска после ошибки; `--abort-open-run <UUID>` отменяет запуск, если он ещё не перешёл в обработку. Клиент повторяет временные ошибки ограниченное число раз, выводит только агрегированный результат и не печатает заголовок авторизации. Полный результат не отправляется, если коллектор сообщает неполноту.

Høringsportalen cursors вычисляются независимо из верхней границы каждого настроенного feed. Пустой feed сохраняет прежний cursor. ODA использует шесть потоков: `Sag`, `Sagstrin`, `SagDokument`, `Dokument`, `Afstemning`, `Sagsstatus`; порядок курсора — точная пара `(opdateringsdato, id)`. Точность дробной части сохраняется. Смещение часового пояса для ODA не предполагается: исходная метка остаётся в метаданных, UTC-поле пустое.

Feed Høringsportalen содержит ограниченный текущий набор записей (до 25 на feed), а не архив. Импорт такого результата не считается полным историческим охватом.

## Запуск, пакеты и восстановление

1. `start` фиксирует UUID, источник, режим, число пакетов, исходные checkpoints и предложенные значения. Один активный запуск на источник обеспечивается уникальным индексом БД.
2. `batch` сначала валидирует пакет, затем атомарно записывает его хеш и staging-записи. Повтор тех же байтов/содержимого идемпотентен; другой payload под тем же индексом отклоняется.
3. `commit` обрабатывает записи небольшими порциями. Публикация, события и отметка staging выполняются одним D1 `batch`. При временной ошибке повтор `commit` продолжает с незавершённых строк.
4. Checkpoints продвигаются только после принятия всех пакетов, обработки всех записей и успешной долговременной записи. При неполной записи, конфликте состояния или ошибке старые checkpoints остаются. Run становится `BLOCKED` или остаётся восстанавливаемым в `COMMITTING`; checkpoint для заблокированного импорта не коммитится.
5. Открытый запуск можно отменить. Запуск в `COMMITTING` нельзя отменить, его нужно повторить до завершения.

Частичные диагностические данные сохраняются в staging; неполная новая публикация может быть сохранена как `source_complete=0`, без событий. Уже сохранённый полный снимок не перезаписывается неполным. Отсутствующая связь в неполном ответе не трактуется как удаление.

## Изменения и исторический режим

Уникальность `(source_id, external_id)` не позволяет источникам пересекаться. Канонизация JSON делает сравнение нечувствительным к порядку ключей; связи сортируются по официальным ID. Повтор идентичного снимка не меняет `updated_at` и не создаёт событие. Значимые различия создают типы `FIRST_SEEN`, `TITLE_CHANGED`, `CONTENT_CHANGED`, `STATUS_CHANGED`, `PUBLICATION_TYPE_CHANGED`, `DOCUMENTS_CHANGED`, `STAGES_CHANGED`, `VOTES_CHANGED` и `RECLASSIFIED`. Изменение только source timestamp или технических метаданных событием не становится. Составные event keys включают run, публикацию, тип и SHA-256 снимка; уникальное ограничение БД защищает повторы, а отдельные переходы A→B→A сохраняются.

Событие в историческом режиме всегда имеет `notify_eligible=0`. В инкрементальном режиме eligibility означает только пригодность события для будущей фильтрации: событие не ставится в очередь и не отправляется. Для `IRRELEVANT`, неполных или заблокированных классификатором записей eligibility равно нулю. Изменение статуса само по себе не утверждает принятие закона или изменение прав.

## Локальная проверка

Из корня проекта:

```sh
python3 -m unittest discover -s tests -v
cd worker
npm run typecheck
npm test
npx wrangler d1 migrations apply denmarktgbot-db --local
npx wrangler d1 execute denmarktgbot-db --local --command "PRAGMA table_info(publications); SELECT name FROM sqlite_master WHERE type='table' ORDER BY name"
```

Worker-тесты запускают локальный Wrangler и временную D1; они проверяют аутентификацию, валидацию, повторы, события, полноту, checkpoints, пакетные сбои и совместимость Telegram/health. Python тесты подменяют HTTP и не обращаются в сеть.

## Границы реализации

Это подготовка слоя хранения и импорта, а не production-включение. Перед эксплуатацией нужно отдельно настроить `INGEST_API_TOKEN`, применить миграцию в целевой среде и выполнить контролируемую проверку. Cloudflare, production D1, webhook и Telegram-секреты этой фазой не меняются. Незавершённые staging-записи и события хранятся без автоматической очистки; retention/cleanup нужно определить до длительных регулярных запусков. Ограничение одного активного запуска действует на уровне БД для каждого source.
